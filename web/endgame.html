HOW IT WORKS

The agent never searches. Every legal move is looked up in a complete table of king and queen (or rook) against a lone king, which was solved offline by retrograde analysis: working backwards from checkmate, each position gets its exact distance to mate, or is marked a draw. The agent plays the fastest win when it is winning and the longest defence when it is losing.

Retrograde analysis

New to this? Most search starts where you are and asks what follows. Retrograde analysis starts at the end and asks what leads to it. Mark the exit of a maze, then every square one step from the exit, then every square one step from those. The whole maze is labelled in one pass, without walking any route through it.

The solver in endgame/retro.py seeds every checkmate with distance 0 and queues it. It pops positions in order of distance and visits each one's predecessors, the positions one quiet move earlier. If the popped position is a loss for the side to move, its predecessor is a win one ply deeper. If it is a win, the move into it is bad for the predecessor, so that position's count of legal moves drops by one. When the count reaches zero, every move loses, and the predecessor is a loss one ply deeper than the last reply decided.

  • Positions that are never decided are draws.
  • A capture never decrements a count: taking the piece leaves king against king, which is a draw.

Distance to mate

New to this? Distance to mate is the number of moves left before checkmate if both sides play perfectly. Picture a countdown to a finish line. The side that is winning wants the number small. The side that is losing wants it large, because that is how long it can hold out.

The table counts plies (half-moves). An odd code means the side to move wins in that many plies. An even code means it is being mated, and 0 means already checkmated.

  • 65534 marks a draw and 65535 an illegal tuple.
  • 65533 appears only while the solver runs, and every one is replaced by a draw before the table is saved.

Table lookup

New to this? The agent does not work the answer out. It reads it from an answer key. For each legal move it reads the stored result of the position that move creates, from its own side's point of view, and picks the best entry.

best_move in endgame/tablebase.py ranks each move with a key. A win beats a draw, and a draw beats a loss. Among wins the fewest plies is best. Among losses the most plies is best. The lone king and the side with the piece use the same key, so one rule gives the fast mate and the longest defence. Ties go to the move generated first.

Checking the table

New to this? A proofreader checks each entry against the rules without trusting whoever wrote it. A winning entry needs a move into a loss one ply shallower, and no faster win. A losing entry needs only winning replies, and the slowest of them must be exactly one ply shorter.

check_positions in endgame/retro.py applies that definition to every legal position, without calling the solver. python -m endgame build runs it after every rebuild.

  • KQK: 0 problems in 368,452 entries. KRK: 0 problems in 399,112 entries.
  • As a test of the checker, 20 corrupted entries in a copy of the table produced 51 reported problems.

Rules: the pieces move as in chess (king, queen, rook), with no pawns, so no promotion or castling. A black king that takes the piece ends in king against king, a draw. The 50-move rule is not applied, so every distance is pure distance to mate.

How these were chosen: nothing is tuned or learned. The moves are the chess rules for these pieces, and the sentinel codes sit at the top of the uint16 range so no real distance can collide with them. The solver is exact, so there is no training. Solve times were 4.9 s (KQK) and 4.4 s (KRK) on a quiet laptop, and 25.0 s and 34.3 s on a shared one. The solver was the same in both runs.
